## 2. 架构原则

1. `MVP 优先`
2. `单体优先`
3. `边界清晰`
4. `AI 与游戏运行时外置`
5. `审计与权限第一版就落地`

本阶段不建议直接上重型微服务。原因不是业务不复杂，而是当前 MVP 的核心目标是尽快跑通：

`建档 -> 同意 -> 评估 -> 风险分级 -> 康复计划 -> 训练 -> 结果回传 -> 医师调整`

在这个阶段，分布式带来的鉴权、链路追踪、部署、排障成本，通常大于收益。

## 3. 总体架构

推荐采用：

`模块化单体 + 独立 AI 服务 + 独立游戏运行时 + 对象存储`

整体分为五层：

1. 前端层
2. 业务后端层
3. AI 服务层
4. 游戏接入层
5. 数据与基础设施层

## 4. 架构分层

### 4.1 前端层

建议先做“两端一壳”：

- 医师/管理员共用一个 Web 后台
- 患者/家属共用一个响应式 Web 端或 PWA
- 训练入口作为单独训练壳层，嵌入体感训练页面或 Unity WebGL 容器

这样做的好处：

- 最快覆盖 `P0` 角色能力
- 设计系统更容易统一
- 路由和鉴权体系更简单
- 后续家属端功能可以逐步开放，而不是一开始做成独立系统

### 4.2 业务后端层

业务后端建议采用 `模块化单体`，统一承载：

- API
- 鉴权
- 数据权限
- 审计
- 事务一致性
- 聚合查询

内部按领域拆模块，而不是拆进程。

推荐模块：

- `identity-access`
- `patient-consent`
- `assessment-ai`
- `rehab-plan`
- `training-content`
- `audit-event`

### 4.3 AI 服务层

AI 服务建议独立部署，不直接暴露给前端，仅由主后端调用。

AI 服务负责：

- 评估结果分析
- 风险等级建议
- 初始康复计划建议
- 训练结果异常标记与辅助建议

重要边界：

- AI 输出在 MVP 阶段只能是 `辅助建议`
- 最终生效风险等级、最终生效计划仍在业务后端落库
- 必须保留模型版本、输入摘要、输出摘要和人工确认痕迹

### 4.4 游戏接入层

游戏接入建议独立看待，不把 Unity 或训练端逻辑塞进主后端。

训练运行时负责：

- 拉取当前授权训练任务
- 上报训练开始/暂停/结束
- 回传结果摘要和动作指标
- 按需上传关键截图、关键帧或结果附件

主后端负责：

- 校验患者是否存在当前生效计划
- 校验训练项目是否在当前计划内
- 生成训练会话与训练结果记录
- 做结果聚合与异常判断

## 5. 技术选型建议

### 5.1 前端

推荐：

- `Next.js`
- `React`
- `TypeScript`
- `Ant Design`

原因：

- 医师后台、管理员后台会有大量列表、表单、详情、筛选、审计页
- Ant Design 对后台场景成熟，能提升首期开发效率
- Next.js 适合同时承载后台和轻量患者端
- TypeScript 便于前后端共享类型和接口约束

### 5.2 后端

推荐：

- `NestJS`
- `TypeScript`
- `Prisma`

原因：

- NestJS 非常适合模块化单体
- 统一 TypeScript 降低前后端沟通成本
- Prisma 对 PostgreSQL 迭代效率高，适合 MVP 快速建模

### 5.3 数据库

推荐：

- `PostgreSQL`

原因：

- 强关系数据多
- 事务要求明确
- 审计、计划版本、授权关系、训练聚合都适合关系型建模
- `jsonb` 可承载评估输入摘要、AI 输出摘要、动作指标摘要等半结构化数据

### 5.4 缓存与队列

推荐：

- `Redis`

用途：

- 会话缓存
- 限流
- 提醒任务
- 训练结果失败补偿
- AI 异步分析任务

### 5.5 AI 服务

推荐：

- `FastAPI`
- `Python`

原因：

- AI 模型接入、推理编排更适合 Python 生态
- FastAPI 足够轻量，接口清晰，适合作为独立服务

### 5.6 游戏接入

推荐：

- `Unity WebGL` 作为首选路线
- 必要时保留独立训练端模式

原因：

- MVP 阶段浏览器内训练接入成本最低
- 后续可根据院内设备情况扩展到 kiosk、Pad 或独立客户端

一期交付策略：

- 优先自研 1 个轻量 Unity WebGL 训练壳，跑通正式训练结果采集闭环。
- 客户已有 Unity 游戏时，不直接改平台业务逻辑，而是按统一 Bridge 协议接入。
- 所有 Unity 游戏必须回传真实结构化结果，包括 `sessionId`、得分、完成率、训练时长、反应时间、动作准确率、运动强度、采集来源和动作指标。
- 平台不接受固定演示成绩、`demo/mock` 来源或缺失动作指标的结果。
- Bridge 协议、SDK 和 Unity 调用模板见 `docs/unity/unity-webgl-bridge-protocol.md`。

### 5.7 对象存储

推荐：

- `MinIO`，私有化优先
- 或兼容 `S3/OSS/COS`

用途：

- 协议/同意留痕附件
- 评估相关文件
- 训练截图和关键帧
- Unity/WebGL 静态资源
- 报表导出文件

### 5.8 可观测性

推荐：

- `OpenTelemetry`
- 应用日志平台

重点监控：

- 训练结果回传
- AI 调用链路
- 核心接口成功率
- 鉴权异常
- 设备异常

## 6. 模块化单体内部拆分

### 6.1 `identity-access`

职责：

- 登录/登出
- JWT/会话
- 角色绑定
- 权限范围
- 当前身份上下文

### 6.2 `patient-consent`

职责：

- 患者建档
- 医师负责关系
- 家属关系绑定
- 同意记录
- 家属共享授权

### 6.3 `assessment-ai`

职责：

- 评估记录
- 风险分级记录
- AI 分析留痕

### 6.4 `rehab-plan`

职责：

- 计划生成
- 计划版本
- 计划项
- 医师调整记录
- 当前生效计划唯一约束

### 6.5 `training-content`

职责：

- 训练内容目录
- 训练会话
- 训练结果
- 动作指标
- 设备登记

### 6.6 `audit-event`

职责：

- 审计日志
- 系统事件日志
- 异常留痕
- 敏感操作记录

## 7. 数据层设计建议

### 7.1 主业务库

`PostgreSQL` 作为唯一主业务库。

建议按 `schema` 或模块前缀分域管理表。

### 7.2 半结构化字段

以下内容建议使用 `jsonb`：

- 评估输入摘要
- AI 输出摘要
- 风险依据摘要
- 动作关键点摘要
- 目标指标
- 审计前后快照摘要

### 7.3 不建议长期入库的数据

- 完整视频流
- 高频原始姿态帧
- 调试阶段的大模型上下文全文

## 8. 权限与审计架构

### 8.1 权限模型

推荐采用：

`RBAC + 数据范围 + 同意范围`

三层控制：

1. `RBAC`
   - 患者
   - 医师
   - 家属
   - 管理员

2. `数据范围`
   - 医师只看本人负责患者
   - 管理员默认不看敏感病历

3. `同意范围`
   - 家属访问受 `caregiver_relation + consent_record` 双重约束

### 8.2 审计模型

分两类日志：

- `audit_log`
  - 谁
  - 何时
  - 对什么对象
  - 做了什么
  - 是否成功

- `system_event_log`
  - 训练上传失败
  - AI 分析失败
  - 登录异常
  - 设备异常
  - 权限拒绝

## 9. 部署拓扑建议

MVP 首期建议只部署 1 个主应用和 2 个外部能力边界：

- 主应用：`Next.js + NestJS + PostgreSQL + Redis`
- AI 服务：`FastAPI`
- 游戏运行时：`Unity WebGL / 训练壳层`
- 共享底座：对象存储、日志、审计、权限控制

### 9.1 环境建议

- `dev`
- `test`
- `staging`
- `prod`

### 9.2 部署方式建议

如果是早期内部验证：

- 可先用容器化部署
- 统一反向代理
- 单独挂载对象存储

如果后续进院或多机构部署：

- 再考虑私有化交付和内网部署适配

## 10. MVP 边界建议

第一阶段只做：

- 1 个主应用
- 1 个 AI 服务
- 1 个或少量训练项目
- 1 条完整训练闭环

不要第一版同时做：

- 多微服务拆分
- 多游戏矩阵
- 多机构协同
- 全量家属端
- 高级 BI 平台

## 11. 推荐目录方向

虽然此文档不要求代码实现，但建议项目初始化时按以下思路组织：

- `apps/web-portal`
- `apps/api-server`
- `apps/ai-service`
- `packages/shared-types`
- `packages/config`
- `packages/ui`（后续可加）
- `docs`

## 12. 进入 UI 设计前，与架构相关必须确认的事项

1. 首发角色范围是否冻结
2. 首发训练内容数量是否冻结
3. 患者端、医师端、管理员端入口是否冻结
4. AI 是同步返回还是异步任务
5. Unity/WebGL 是否作为首发训练容器
6. 对象存储是否私有化
7. 登录方式是否只做账号密码
8. 审计与权限是否第一版即落库
