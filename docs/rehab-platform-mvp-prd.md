# 阿尔茨海默病 AI+体感康复平台 MVP 需求文档

## 1. 文档说明

- 文档版本：`v0.1`
- 文档类型：`MVP PRD 草案`
- 目标：用于新项目立项、需求对齐、UI 低保真设计、技术架构设计与研发拆解
- 适用阶段：`从 0 到 1 的第一阶段`

## 2. 需求来源

本 PRD 基于以下来源整理并收敛为可开发的 MVP 范围：

- 客户提供的需求说明文档
- 客户提供的中期汇报材料
- 客户现有演示项目中已体现的业务方向

本 PRD 不直接照搬客户的“全量愿景”，而是将其拆分为：

- `P0`：必须先做、必须闭环
- `P1`：MVP 后可增强
- `P2`：平台化与智能化扩展

## 3. 产品背景

阿尔茨海默病及相关认知障碍人群在康复过程中，普遍面临以下问题：

- 训练依从性低，患者难以长期坚持
- 个体化干预不足，训练方案难以因人而异
- 家庭照护负担重，家属难以理解并有效辅助
- 院外训练过程不可见，医师难以及时了解患者状态变化
- 传统训练结果量化不足，缺少结构化追踪和复盘依据

随着 AI 评估、动作识别、体感交互与远程管理技术的发展，具备“智能评估 + 体感训练 + 数据追踪 + 家庭协同”能力的数字化康复平台，可以在提升康复效率、增强训练趣味性、降低照护门槛和强化医患协同方面提供现实价值。

本项目拟建设一个“阿尔茨海默病 AI+体感康复平台”，面向患者、医师、家属和管理员，提供基础评估、风险分级、康复计划、体感训练、训练结果回看与基础管理能力，支撑院内外一体化康复闭环。

## 4. 产品目标

### 4.1 产品目标

建设一个面向阿尔茨海默病康复场景的轻量化数字平台，帮助患者完成可执行、可记录、可追踪的康复训练闭环，帮助医师实现训练方案下发与疗效观察，帮助家属参与陪护与监督，帮助机构完成基础运营管理。

### 4.2 业务目标

1. 提升患者康复训练的参与度与完成率。
2. 提高医师制定训练方案和追踪训练结果的效率。
3. 降低家属在院外陪护和训练监督中的理解与执行门槛。
4. 建立患者训练数据沉淀，为后续个性化推荐与疗效分析提供基础。

### 4.3 MVP 目标

MVP 阶段聚焦验证以下核心假设：

1. 患者是否能够在简单引导下完成基础体感康复训练。
2. 医师是否能够通过平台完成患者建档、训练方案配置及结果查看。
3. 家属是否能够有效参与训练提醒与结果查看，提升训练依从性。
4. 平台是否能够稳定采集训练记录、完成情况与基础评估数据，形成最小可用闭环。

MVP 不追求完整疾病管理体系，而优先验证“评估 -> 方案 -> 训练 -> 记录 -> 回看”的核心链路是否成立。

## 5. 角色定义与优先级

### 5.1 角色定义

#### 患者

阿尔茨海默病或轻中度认知障碍康复对象，是训练执行的核心主体。

主要诉求：

- 操作简单
- 反馈及时
- 训练有引导
- 流程不复杂

#### 医师

包括康复医师、治疗师、认知训练师等专业人员，是方案制定与效果评估的核心角色。

主要诉求：

- 快速建档
- 便捷配置训练计划
- 查看训练结果与依从性
- 掌握患者变化趋势

#### 家属

患者的主要照护者或陪护者，是训练执行的重要辅助角色。

主要诉求：

- 理解训练任务
- 接收提醒
- 查看完成情况
- 必要时协助患者完成训练

#### 管理员

平台或机构运营管理人员，负责账号、机构、设备、内容与基础数据管理。

主要诉求：

- 系统可配置
- 账号可控
- 数据可查看
- 运行可维护

### 5.2 角色优先级

- `P0 角色`：患者、医师
- `P1 角色`：家属
- `P2 角色`：管理员

说明：

- MVP 的核心是验证训练闭环，患者负责执行训练，医师负责配置与评估，因此两者优先级最高。
- 家属对提升依从性很重要，但在 MVP 阶段定位为“辅助参与”。
- 管理员能力在 MVP 阶段只覆盖基础支撑，不作为第一轮价值验证核心。

## 6. MVP 范围定义

### 6.1 P0 功能范围

#### 患者端

1. 患者基础信息建立与档案绑定
2. 查看当日或当前训练任务
3. 进入指定体感训练并完成训练流程
4. 训练过程中的基础语音或图形引导
5. 训练完成后的结果反馈
6. 查看历史训练记录

#### 医师端

1. 患者建档与基础信息管理
2. 患者评估结果录入与查看
3. 训练计划配置与下发
4. 查看患者训练完成情况与基础结果数据
5. 查看患者历史记录与依从性概览

#### 平台能力

1. 账号登录与基础权限区分
2. 训练项目管理
3. 训练记录自动采集与存储
4. 基础数据列表与概览展示
5. 体感识别能力接入，支持 MVP 选定训练动作的识别与判定

### 6.2 P1 功能范围

#### 家属协同

1. 家属账号绑定患者
2. 查看训练计划与训练完成情况
3. 接收训练提醒或未完成提醒
4. 查看基础康复建议或注意事项

#### 患者体验增强

1. 训练过程中的鼓励式反馈
2. 训练难度分级
3. 简单的阶段性成就展示

#### 医师效率增强

1. 患者分组管理
2. 模板化训练方案
3. 阶段性结果趋势展示

#### 运营支撑

1. 基础设备状态管理
2. 训练内容启停配置
3. 基础操作日志与审计

### 6.3 P2 功能范围

1. 基于 AI 的个性化训练推荐
2. 基于训练表现与评估结果的风险预警
3. 多维度认知能力画像与康复进展分析
4. 多机构管理与跨机构协同
5. 远程视频康复指导
6. 更丰富的训练内容库与游戏化训练机制
7. 与医院 HIS/EMR、随访系统、可穿戴设备的数据打通
8. 面向科研的脱敏数据分析与导出
9. Unity 多游戏矩阵与统一账号/数据打通

### 6.4 非 MVP 范围

以下内容不纳入本次 MVP：

1. 完整医疗诊断支持与临床决策系统
2. 高复杂度 AI 自学习与自动处方能力
3. 全病程管理体系
4. 面向重度患者的复杂交互训练方案
5. 医保结算、商业付费与财务系统
6. 多院区、多租户、集团化运营能力
7. 患者、家属、医师三端独立原生 App 全量建设
8. 大规模第三方硬件标准化集成
9. 精细化内容运营体系
10. 科研级高级统计分析平台

### 6.5 范围界定原则

1. MVP 只覆盖核心训练闭环，不追求大而全。
2. 凡不能直接支撑“患者完成训练、医师下发和回看、数据可沉淀”的功能，原则上不进入 `P0`。
3. 优先保证流程跑通、识别稳定、记录准确、角色职责清晰。
4. 增强体验类、复杂智能类、平台化扩展类能力优先放入 `P1/P2`。

## 7. 核心业务闭环

本平台 MVP 的核心业务闭环为：

`患者建档/导入 -> AI评估 -> 风险分级 -> 康复计划匹配 -> 游戏化训练执行 -> 训练结果回传 -> 医师查看与调整 -> 进入下一轮训练`

目标是在最小可用范围内，完成“可评估、可干预、可追踪、可调整”的康复管理闭环。

### 7.1 主流程概述

1. 患者完成基础信息建档，并进入初始评估流程。
2. 系统基于量表、问答、行为表现及体感交互数据进行 AI 评估。
3. 系统输出风险分级结果，并生成对应的康复干预建议。
4. 系统根据风险等级、能力画像和训练目标，匹配个性化康复计划。
5. 患者按计划进入体感游戏训练，系统记录训练过程与结果数据。
6. 训练结果自动回传至患者档案，形成阶段性训练记录与趋势视图。
7. 医师或康复师查看评估与训练结果，必要时调整训练计划。
8. 调整后的计划重新下发，患者进入下一轮训练。

### 7.2 MVP 闭环目标

- 首次评估后，系统必须能生成一份可执行的初始康复计划。
- 每次训练完成后，系统必须能形成结构化训练结果并归档。
- 医师必须能基于结果查看、确认或调整康复计划。
- 患者在整个周期内始终只有一个“当前生效计划”。
- 平台支持按“评估周期 + 训练周期 + 复盘周期”持续管理患者。

## 8. 功能需求

### 8.1 AI 评估

#### 功能目标

通过标准化评估流程形成患者的认知与运动能力初始画像，为风险分级和计划推荐提供依据。

#### P0 功能要求

- 支持患者基础档案录入或导入，包括姓名、编号、年龄、性别、既往病史、照护信息等基础字段。
- 支持初始评估任务发起，并标记评估状态：`未开始/进行中/已完成/失败`。
- 支持采集以下至少一类评估数据：
  - 基础问答或量表数据
  - 简单认知任务表现数据
  - 体感交互过程数据
- 支持 AI 对评估数据进行综合分析，输出结构化评估结果。
- 评估结果至少包含：
  - 当前认知状态概览
  - 动作或反应能力概览
  - 训练适配建议
  - 风险分级结果
- 支持保存评估时间、评估版本、评估结论，作为后续对比基线。
- 支持查看最近一次评估结果及历史评估记录。

#### 业务规则

- 未完成初始评估的患者不可直接进入正式训练计划。
- 同一患者任一时点只能有一个“当前有效评估结果”作为计划匹配依据。
- 评估失败或数据缺失时，系统应提示重新评估或人工补充判断。

### 8.2 风险分级

#### 功能目标

基于评估结果对患者进行风险分层，为康复计划强度、频次和内容提供决策依据。

#### P0 功能要求

- 支持系统根据评估结果自动生成风险等级。
- 风险等级至少支持三级：
  - 低风险
  - 中风险
  - 高风险
- 支持展示风险分级的主要判断依据摘要。
- 支持在患者详情页展示当前风险等级及分级时间。
- 支持将风险等级作为计划匹配的必选输入条件。
- 支持医师对系统生成的风险分级进行人工确认或修正。

#### 业务规则

- 高风险患者默认进入更保守的训练策略。
- 风险等级变化后，应触发计划重新评估与匹配。
- 若医师人工修正风险等级，应保留系统原始结果与人工修正记录。

### 8.3 计划匹配

#### 功能目标

将评估结果与风险等级转化为可执行的个体化康复训练计划。

#### P0 功能要求

- 支持系统基于以下信息生成初始康复计划：
  - 风险等级
  - 认知能力画像
  - 动作能力画像
  - 训练目标
- 计划内容至少包括：
  - 训练周期
  - 每周训练频次
  - 每次训练时长
  - 推荐训练项目或游戏组合
  - 难度等级
  - 阶段目标
- 支持计划状态管理：`待确认/生效中/已暂停/已结束`。
- 支持患者侧查看当前训练计划摘要。
- 支持医师或康复师查看系统推荐计划，并进行确认或修改后下发。
- 支持记录计划版本，确保每次调整可追溯。
- 支持计划与患者当前风险等级、评估结果建立关联。

#### 业务规则

- 初始计划必须由系统生成，医师可在此基础上调整。
- 生效中的计划仅允许存在一个版本。
- 当患者风险等级或阶段结果发生显著变化时，应支持发起重新匹配。
- 暂停状态的计划不可继续发起训练任务。

### 8.4 游戏训练

#### 功能目标

通过体感交互式游戏承载康复训练，提高训练执行率和参与度，并沉淀过程数据。

#### P0 功能要求

- 支持患者按当前计划进入训练任务。
- 支持按计划下发对应的体感游戏训练项目。
- 每个训练项目至少应配置：
  - 游戏名称
  - 对应训练目标
  - 训练时长
  - 难度等级
  - 开始/结束条件
- 支持训练过程中的基础状态控制：
  - 开始训练
  - 暂停训练
  - 继续训练
  - 结束训练
- 支持采集训练结果数据，至少包括：
  - 完成情况
  - 完成时长
  - 正确率或得分
  - 反应时间或动作完成度
  - 中断或退出情况
- 支持训练完成后自动生成单次训练记录。
- 支持患者查看本次训练是否完成及基础结果反馈。

#### 业务规则

- 患者仅能执行当前生效计划内的训练内容。
- 训练中断时，系统应记录中断原因或状态，不得直接视为完成。
- 训练结果必须与患者、计划、具体训练项目绑定。

### 8.5 结果回传

#### 功能目标

将训练过程与结果自动沉淀为可追踪数据，支撑阶段评估和计划优化。

#### P0 功能要求

- 支持单次训练结束后自动回传训练结果至患者档案。
- 支持按患者维度汇总以下结果信息：
  - 训练次数
  - 完成率
  - 平均得分
  - 平均时长
  - 趋势变化
- 支持生成阶段性结果视图，用于医师快速判断训练效果。
- 支持结果按时间维度查看，至少支持：
  - 单次训练记录
  - 近 7 天或近 30 天训练概览
  - 按计划周期查看
- 支持将训练结果与初始评估、最近一次评估进行关联展示。
- 支持标记异常结果，如连续未完成、成绩持续下降、长时间未训练。

#### 业务规则

- 每次训练完成后必须自动生成结构化记录。
- 若结果回传失败，系统应有补偿机制，避免训练记录丢失。
- 异常结果应进入医师可见视图，支持后续人工干预。

### 8.6 医师调整

#### 功能目标

让医师或康复师基于评估和训练结果对系统建议进行审核与修正，保证干预方案安全、有效、可持续。

#### P0 功能要求

- 支持医师查看患者完整闭环信息：
  - 最近评估结果
  - 当前风险等级
  - 当前生效计划
  - 单次及阶段训练结果
- 支持医师对系统推荐计划进行以下调整：
  - 修改训练频次
  - 修改单次训练时长
  - 调整训练项目组合
  - 调整难度等级
  - 暂停或结束当前计划
- 支持医师记录调整原因与调整时间。
- 支持调整后生成新计划版本，并自动替换当前生效计划。
- 支持医师发起复评，以重新进入“评估 -> 分级 -> 计划匹配”流程。
- 支持保留调整前后差异，满足追溯需求。

#### 业务规则

- 医师调整后的计划优先级高于系统自动推荐结果。
- 医师手动调整后，患者端应仅展示最新生效版本。
- 对于高风险患者，关键计划变更应要求医师明确确认后生效。

## 9. 关键业务对象与状态

### 9.1 患者

- 必须存在唯一患者档案
- 必须关联评估记录、风险等级、康复计划、训练记录

### 9.2 评估记录

- 状态：`未开始/进行中/已完成/失败`
- 必须记录评估时间、结果摘要、风险分级结果

### 9.3 康复计划

- 状态：`待确认/生效中/已暂停/已结束`
- 必须支持版本化
- 必须与评估结果和风险等级关联

### 9.4 训练记录

- 状态：`未开始/进行中/已完成/已中断`
- 必须关联患者、计划、训练项目、结果数据

## 10. 数据要求

### 10.1 核心数据对象定义

#### 10.1.1 用户与身份

**用户（User）**

核心字段：

- `user_id`
- `手机号/账号`
- `登录方式`
- `角色类型`
- `账号状态`

## 11. 权限、安全与隐私要求

### 11.1 权限控制要求

MVP 采用基于角色的权限控制（RBAC），最小化开放数据访问范围。

#### 患者

- 可查看并维护本人基础资料
- 可查看本人同意记录、评估结果、康复计划、训练记录
- 可发起或撤回家属共享授权
- 不可查看其他患者数据
- 不可修改医生确认后的正式评估结论

#### 医生

- 可查看本人负责患者的完整业务数据
- 可创建与调整康复计划
- 可查看 AI 辅助评估与训练分析结果
- 可确认或驳回 AI 建议
- 不可访问非本人管理患者的数据，除非平台管理员明确授权

#### 家属或照护者

- 仅可查看患者授权范围内的数据
- 默认可查看训练进展、计划摘要、提醒信息
- MVP 默认不可查看完整病史与全部原始评估输入，除非患者或监护人单独授权

#### 管理员

- 可管理账号、角色、内容、配置
- 可查看脱敏后的平台运营数据和审计日志
- 默认不可查看患者详细病历、原始评估内容、完整训练明细，除非具备合规授权的专门管理权限

### 11.2 隐私同意要求

MVP 必须具备明确、可追溯的同意机制，至少覆盖以下场景：

- 注册或首次使用时的用户协议与隐私政策同意
- 首次启用摄像头体感训练时的摄像头采集同意
- 首次使用 AI 评估或 AI 建议时的 AI 数据处理同意
- 家属查看患者数据前的共享授权同意
- 监护人代替患者完成同意时的身份说明与留痕

MVP 要求：

- 未完成必要同意前，不得进入对应功能
- 同意记录必须版本化保存
- 用户可查看已同意内容及时间
- 用户撤回后，后续数据采集与共享应立即停止

### 11.3 审计要求

MVP 必须记录以下关键审计事件：

- 登录、登出、登录失败
- 患者档案创建、修改
- 同意记录创建、撤回
- 评估发起、结果生成、医生确认或修改
- 康复计划创建、调整、停用
- 训练结果上传、异常中断
- 患者数据查看、导出、共享授权变更
- 角色变更、权限变更、账号冻结或启用
- 管理员敏感操作

审计要求：

- 日志默认不可被业务用户修改或删除
- 审计日志支持按时间、用户、对象检索
- 审计信息需保留“谁、何时、对什么、做了什么、结果如何”

### 11.4 加密要求

#### 传输加密

- 所有 Web、API、文件上传接口必须使用 HTTPS/TLS
- 禁止明文传输用户身份信息、患者资料、评估结果

#### 存储加密

- 用户密码必须采用不可逆加密存储
- 以下字段至少进行库级或字段级加密存储：
  - 姓名
  - 手机号
  - 联系地址
  - 紧急联系人信息
  - 病史摘要
  - 原始评估输入
  - 高敏感 AI 分析结果
- 如使用对象存储保存附件或报告，需设置私有访问权限与带时效的访问链接

### 11.5 脱敏要求

MVP 应支持最基本的数据脱敏能力，适用于后台展示、日志、导出、运营统计等场景。

脱敏原则：

- 非必要不展示直接身份标识
- 管理后台默认展示脱敏手机号、脱敏姓名
- 审计日志与系统日志中不得记录完整身份证号、完整手机号、完整病史文本
- AI 调试或错误日志中不得落入原始敏感输入全文
- 统计报表默认以聚合数据展示，不直接暴露单个患者身份

## 12. MVP 验收标准

### 12.1 功能验收标准

#### 数据对象与业务闭环

MVP 上线前，以下核心数据对象必须完成建模并贯通：

- 用户
- 患者档案
- 同意记录
- 评估记录
- AI 分析记录
- 康复计划
- 训练会话
- 训练结果
- 审计日志

验收标准：

- 各对象可完成创建、查询、关联
- 患者从“建档 -> 同意 -> 评估 -> 计划 -> 训练 -> 结果查看”形成闭环
- 医生可查看患者结果并调整计划
- 家属可在授权范围内查看进展摘要

#### 权限验收

- 患者无法访问他人数据
- 家属未获授权时无法查看患者信息
- 医生仅可访问本人负责患者数据
- 管理员默认不可查看患者完整敏感详情
- 任一越权访问均返回明确拒绝结果，并产生审计记录

#### 同意与隐私验收

- 未同意隐私政策时无法进入核心业务流程
- 未同意摄像头采集时无法启用体感训练
- 未同意 AI 数据处理时不可触发 AI 评估或 AI 建议
- 同意记录可追溯到版本、时间、主体、设备/IP
- 撤回授权后，后续共享和采集立即停止

#### 审计验收

- 关键操作均生成审计日志
- 日志中可查询操作人、对象、时间、动作、结果
- 日志不可被普通业务角色编辑或删除
- 管理员可按患者、用户、时间范围查询日志

#### 加密与脱敏验收

- 平台全链路启用 HTTPS
- 密码非明文存储
- 约定的敏感字段已加密或受控存储
- 管理后台与日志中的敏感信息按规则脱敏
- 文件访问具备权限控制与失效机制

### 12.2 业务结果验收标准

MVP 至少满足以下业务可用性目标：

- 患者可独立或在家属协助下完成一次完整建档与训练流程
- 医生可完成至少 1 名患者的评估结果查看与康复计划调整
- 患者完成至少 1 次体感训练并生成结构化结果
- 家属可查看患者训练进展与计划摘要
- 管理员可完成账号管理、内容启停、审计查询的基础操作

## 13. 非功能要求

### 13.1 可用性

- 核心业务流程可用率不低于 `99.0%`
- 登录、查看计划、提交训练结果等核心接口在正常网络下应稳定可用
- 单点故障不应导致核心数据丢失

### 13.2 性能

- 普通页面打开时间目标不高于 `3 秒`
- 核心查询接口平均响应时间目标不高于 `2 秒`
- 训练结果提交后 `5 秒` 内可在患者端和医生端查询到
- 支持 MVP 规模下并发用户稳定使用

### 13.3 数据完整性

- 患者、评估、计划、训练结果之间关联关系完整
- 关键业务记录具备创建时间、创建人、状态字段
- 训练中断、提交失败等异常场景需保留状态，避免“假完成”或数据静默丢失

### 13.4 可靠性与恢复

- 关键业务数据须具备定期备份机制
- 发生系统异常后可恢复最近有效数据
- 上传失败、网络中断时应支持重试或错误提示，不允许无提示失败

### 13.5 可审计性

- 所有关键操作具备可检索、可追溯记录
- 系统异常、权限拒绝、敏感数据访问必须可追踪

### 13.6 隐私与合规基线

- 遵循“最小必要、最小权限、默认保护”原则
- AI 输出仅作为辅助意见展示，不作为唯一医疗决策依据
- MVP 默认不长期保存完整视频流，优先保存结构化动作指标与训练结果
- 对外展示、运营统计、测试环境数据均应脱敏

### 13.7 兼容性

- 患者端优先支持主流桌面浏览器和常见平板设备
- 体感训练功能需明确浏览器、摄像头、网络环境的最低要求
- 当体感能力不可用时，应给出清晰提示，不得出现无反馈失败

## 14. MVP 成功指标

建议在第一阶段试点中至少追踪以下指标：

- 患者首次评估完成率
- 患者首次训练完成率
- 7 日训练留存率
- 医师计划下发成功率
- 医师对系统推荐计划采纳率
- 训练结果回传成功率
- 体感识别有效率
- 越权访问拦截成功率
- 同意记录留存完整率

## 15. 当前阶段关键假设

1. `P0` 先做 `1 个标准化训练闭环 + 1 个或少量训练游戏`，不在第一版铺开完整游戏矩阵。
2. `P0` 先采用 Web 平台 + 摄像头体感路线，Unity 全量游戏接入列入 `P1/P2`。
3. AI 在 MVP 阶段定位为“辅助评估、辅助建议、辅助分级”，最终计划确认权属于医师。
4. 患者端强调低认知负担，医师端强调高信息密度，管理端强调清晰与可审计。
