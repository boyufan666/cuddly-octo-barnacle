# MiMo 调用结果政策资料包

`docs/templates/mimo-provider-outcome-policy.template.json` 是 P0 outcome/outbox 后续阶段的客户输入模板。第一阶段持久化账本已实施，但人工对账、供应商状态查询、TTS 资产和财务结算仍必须由客户的法务、临床、财务、运维和 MiMo 账户责任方共同冻结；填写副本必须保存在客户控制的私有资料目录，且不得提交供应商密钥、患者资料或原始音频到 Git。

数据模型、状态机、事务边界和四类业务链的技术设计见 [MiMo outcome/outbox design](mimo-provider-outcome-outbox-design.md)。该设计不替代本资料包的正式政策输入。

在开始受控结果读取、供应商状态查询、TTS 资产持久化或财务结算前，使用 Node 24 校验客户批准的副本：

```bash
mise x node@24.14.1 -- node scripts/verify-mimo-provider-outcome-policy.mjs -- /secure/customer/mimo-provider-outcome-policy.json
```

校验器只接受完整、明确且可审计的决策。它要求 MiMo 上游确认幂等键能力、传输位置、字段名、到期时间与证据；状态查询可由客户批准为按幂等键的供应商 API、按供应商请求 ID 的 API，或按关联 ID 的供应商支持工单，但必须明确对应查询身份、过程证据、人工对账负责人、升级路径和 SLA。四条当前高成本链路均携带患者和执行者上下文，因此上游与本地规范化请求身份都必须精确涵盖机构、操作、患者、执行者和规范化请求；不得把这些边界隐含在自由文本中。

计费来源、STT 时长计费方法与单位、预留到期、确认成功后的结算、未确认结果的财务决定、已确认/未确认结果的关闭动作、TTS 资产存储类别、媒体类型、删除方法和各类留存期限均为客户批准的输入。校验器要求每项输入有明确值、负责人、SLA 或可追溯的政策/合同依据，但不会把 `HTTP Header`、特定 MiMo 查询接口、退款、额度释放、对象存储或某个计费公式当成默认政策。后续实施必须逐项映射这些输入；不能用任意一个被接受的输入替代另一个输入。

以下情况必定失败，且不得通过 waiver、示例、seed、演示、手工改库、自动重试、新键重投或任何 fallback 放行：缺字段、额外字段、占位符、`unknown`/`TBD` 等不确定标记、缺少上游幂等或可追溯状态查询、未包含患者或执行者的身份作用域、同键异 payload 外呼、未指定负责人或 SLA、自动财务调整、未加密的 outcome/TTS 资产，或没有受控新付费请求批准的重发。

通过该资料包校验仅代表政策输入齐备，**不代表** outcome/outbox 已实现或可上线。后续实现必须将每项政策逐一映射到数据库约束、事务性 outbox、上游调用、状态查询、人工案件、访问控制、保留/删除任务、审计和真实回归；未完成前 Production 保持 `BLOCKED`。
