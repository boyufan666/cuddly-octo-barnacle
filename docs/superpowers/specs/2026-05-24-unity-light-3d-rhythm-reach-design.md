# Unity Light 3D Rhythm Reach Design

## Goal

Build a self-developed Unity WebGL prototype for a light 3D rehabilitation training game named `rhythm_reach_3d`. The prototype must prove the Unity route without pretending that browser games or placeholder files are Unity. It should be suitable for later WebGL build verification and platform integration through the existing rehabilitation training bridge.

## Product Positioning

The platform itself remains a web-based rehabilitation management system. Unity is used only for the training game module where 3D interaction, spatial targets, and stronger customer-facing presentation matter.

The first Unity game should be a light 3D rhythm reach training game:

- A simple clinical-futuristic training room with a forward lane and glowing targets.
- Targets appear in left, right, high, middle, and low zones.
- The user performs timed reach or slash actions to hit targets.
- The game records training duration, target count, hit count, reaction times, motion accuracy, and difficulty level.
- The result is submitted through the existing Unity WebGL bridge protocol `1.0.0`.

The prototype should not become a heavy 3D game. It should avoid character systems, open-world environments, multiplayer, complex physics, paid assets, and unverified third-party SDKs.

## Current Environment Boundary

The current development machine does not have Unity Editor or Unity Hub installed. Therefore this work can create and review Unity project source files, C# scripts, WebGL bridge files, manifest templates, and integration documentation, but it cannot honestly produce a real Unity WebGL build on this machine.

Allowed deliverables before Unity Editor is installed:

- Unity project folder and source code.
- C# runtime scripts.
- WebGL `.jslib` bridge.
- WebGL template files that load `/unity/rehab-unity-bridge.js`.
- Manifest template and build checklist.
- Platform integration documentation.

Not allowed before Unity Editor build:

- Fake `.loader.js`, `.framework.js`, `.data`, or `.wasm` files.
- Claiming the Unity game is already built or browser-runnable.
- Registering placeholder Unity assets as released production content.

## Architecture

The Unity prototype will live in a dedicated project folder, separate from the web and API apps, so the Unity source can be opened by Unity Editor without coupling it to Next.js or NestJS internals.

Recommended folder:

```text
unity/rhythm-reach-3d/
  Assets/
    Plugins/WebGL/RehabTrainingBridge.jslib
    Rehab/
      Scripts/
      WebGLTemplates/RehabWebGL/
      Scenes/
      Materials/
      Prefabs/
  Packages/
  ProjectSettings/
  README.md
```

WebGL build output, once generated by Unity Editor, must be copied to:

```text
apps/web/public/unity/rhythm_reach_3d/0.1.0/
  Build/
  StreamingAssets/
  manifest.json
```

The web platform already owns the runtime bridge file:

```text
apps/web/public/unity/rehab-unity-bridge.js
```

The Unity WebGL template must load that file and expose `window.RehabTrainingRuntimeConfig`. Missing required runtime config is a hard blocker.

## Unity Runtime Components

The Unity project should be split into focused scripts:

- `GameSessionController`: owns session start, countdown, running state, end state, and result submission.
- `RhythmTargetSpawner`: creates 3D targets according to the current difficulty and target schedule.
- `TargetHitDetector`: determines whether a reach or slash hits the active target within the allowed timing window.
- `MetricsAccumulator`: records target appearances, hits, misses, reaction times, visibility samples, and motion accuracy samples.
- `DifficultyController`: adjusts speed, target density, and active zones based on configured difficulty. It must use explicit settings, not hidden fallback values.
- `PoseInputBridge`: receives body tracking input when available in a later phase. In the first Unity-only prototype, mouse or keyboard may be used only as editor development input and must be marked as non-production input.
- `TrainingResultBuilder`: converts accumulated metrics into the bridge protocol payload.
- `RehabTrainingResultBridge`: calls the WebGL `.jslib` function `Rehab_PostTrainingResult(json)`.

## Data Flow

1. The platform creates a real training session and prepares runtime config with `sessionId`, `gameRunId`, `gameCode`, `gameVersion`, `deviceCode`, and `bridgeProtocolVersion`.
2. The Unity WebGL page starts only if required runtime config exists.
3. Unity starts a training session and spawns 3D targets.
4. Each target records `spawnedAt`.
5. Each valid hit records `hitAt`, zone, target id, reaction time, and accuracy signal.
6. Missed targets are recorded when the timing window expires.
7. At the end, Unity builds a result payload with score, completion rate, duration, reaction time, motion accuracy, exercise intensity, metrics summary, and motion metrics.
8. Unity calls `Rehab_PostTrainingResult(json)`.
9. `RehabTrainingBridge.jslib` calls `window.RehabUnityBridge.postTrainingResultJson(json)`.
10. The web platform receives the event and submits it through existing training result APIs.

## Metrics

The prototype must compute metrics from the actual training run:

- `reaction_time_ms`: median or average time between target spawn and hit.
- `target_hit_rate`: hit targets divided by total spawned targets.
- `arm_raise_accuracy`: average target-zone hit accuracy for successful targets.
- `pose_visibility_avg`: average pose input visibility when real pose input exists. In editor-only mouse or keyboard development mode, this metric must not be submitted as a production body-tracking metric.
- `duration_seconds`: actual elapsed training seconds.
- `difficulty_level`: explicit difficulty used for the run.

The result payload must not contain fixed scores, random fake metrics, `mock`, `demo`, `seed_import`, or silently generated default values.

## Error Handling

The prototype must hard-block instead of falling back in these cases:

- Missing `window.RehabTrainingRuntimeConfig`.
- Missing `sessionId`, `gameRunId`, or `gameVersion`.
- Bridge protocol mismatch.
- `RehabUnityBridge` missing from the WebGL template.
- `.jslib` call failure in WebGL.
- No valid training samples when ending a session.
- Pose-based production mode enabled but camera or pose quality is not available.

Development-only input mode is allowed inside Unity Editor to test gameplay, but it must be explicitly labelled and excluded from production build acceptance.

## Visual Direction

Use a light 3D clinical-futuristic style:

- Calm blue-green medical lighting.
- Soft glowing targets and lane markers.
- Minimal training-room geometry made from Unity primitives.
- Clear contrast and large target shapes for older users.
- Immediate visual and audio feedback for hits and misses.

Avoid dark sci-fi overload, paid assets, copyrighted music, realistic patient avatars, or visual effects that make targets hard to read.

## Build And Manifest Requirements

The real WebGL build must be generated only by Unity Editor with WebGL Build Support installed. After building, create a manifest containing:

- `gameCode`: `rhythm_reach_3d`.
- `gameVersion`: `0.1.0` for the first prototype.
- `runtimeType`: `unity_webgl`.
- `bridgeProtocolVersion`: `1.0.0`.
- Unity Editor version.
- Build generated time.
- Source commit.
- Build file list with SHA256 hashes.
- Required runtime config keys.
- Metric definitions.
- Third-party license list.

The manifest must not mark the build as released until the real WebGL files exist and pass verification.

## Testing And Acceptance

Source-level acceptance before Unity Editor:

- Unity project source files exist in the expected folder.
- C# scripts have clear responsibilities.
- `.jslib` contains `Rehab_PostTrainingResult(json)`.
- WebGL template loads `/unity/rehab-unity-bridge.js`.
- Documentation states that no WebGL build exists yet.

Build-level acceptance after Unity Editor:

- Unity WebGL build produces real `.loader.js`, `.framework.js`, `.data`, and `.wasm` files.
- Manifest hashes match the generated files.
- Browser network panel shows actual Unity WebGL resources loading.
- Training can start, spawn targets, register hits and misses, end, and emit `training_result`.
- The emitted event passes `rehab-unity-bridge.js` validation.
- The platform stores `training_session`, `training_result`, `motion_metric`, and `audit_log` records.
- Missing config, duplicate submit, and invalid result payload are blocked.

## Open Decision

The first implementation should create Unity project source and integration files only. A real WebGL build requires installing Unity Editor and WebGL Build Support on a development machine.
